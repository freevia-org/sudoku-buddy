# Sudoku Buddy private feedback intake

This is the private upload endpoint for Sudoku Buddy report ZIP files. It is deployed separately from the Android build at the URL configured in the release build. The endpoint has no read/list API and returns a SHA-256 receipt. A separate, explicit training consent can retain a copy in a private R2 bucket until the user requests deletion.

## Storage and limits

- `POST /v1/reports` accepts only `application/zip` with a decimal `Content-Length` that exactly matches the streamed body.
- The body is read incrementally and stopped as soon as it exceeds the declared length or the 20 MiB hard cap. It is buffered only after bounded collection so it can be hashed and written to Workers KV.
- The first four bytes must match a ZIP local-file, empty-archive, or spanning signature. This is a quick format check, not a full ZIP safety scan; moderators must treat all report contents as untrusted.
- The SHA-256 digest is the receipt and KV key (`reports/<sha256>.zip`), making identical submissions idempotent. No submitter name, email, app installation ID, timestamp, or source IP is stored in a separate record.
- Each report receipt stores its original absolute 90-day expiry in its Durable Object before the first KV write, and writes that same timestamp to KV on retries. A stale-negative KV read or a Durable Object restart cannot reset the analysis deadline. Cloudflare deletes an expiring key when its deadline is reached. Every corrected revision has a distinct receipt and its own deadline.
- The KV account value limit is 25 MiB; this service caps values at 20 MiB. This queue is intended for a bounded, low-volume pilot. KV is eventually consistent and does not provide an atomic compare-and-set; identical simultaneous submissions still converge on the same content-addressed key, but only one request may report `accepted`.
- Training retention is enabled only when `X-Sudoku-Training-Consent` is exactly `yes`. Missing, differently cased, or any other value leaves the report in the 90-day KV analysis queue only. With consent, the Worker also writes the ZIP to the private `TRAINING_EXAMPLES` R2 binding under the lowercase 64-character SHA-256 receipt. R2 has no public URL or read/list API in this Worker. The bucket is long-lived and the consented copy remains until its receipt is deleted; never enable public access for it.
- If the KV write succeeds but the R2 write fails, the request returns `503` and does not claim acceptance. The KV report still follows its original 90-day expiry. The client can safely retry the same ZIP with the same consent header: the content-addressed KV key will be reused and the R2 write retried without refreshing the KV expiry. The app should keep the report pending until it receives a success response.
- Upload and deletion for each receipt are serialized by its own SQLite-backed Durable Object, so a delayed upload cannot recreate R2 data after a completed delete. Each object uses a per-receipt promise queue across KV/R2 I/O; unrelated receipts use separate objects. Deletion writes a durable tombstone first; subsequent uploads of that same receipt return `410`. Tombstones are retained to prevent resurrection.
- `DELETE /v1/reports/<receipt>` deletes the matching service KV and R2 objects. The receipt must be exactly 64 lowercase hexadecimal characters. A complete deletion returns HTTP 200 JSON `{ "receipt": "…", "status": "deleted" }`; repeating it after both stores are empty returns `{ "receipt": "…", "status": "already_deleted" }`. If either store check or deletion fails, the endpoint returns non-2xx `{ "error": "deletion_incomplete", "retry": true }` and never claims success. Retry the same receipt until the endpoint confirms completion. Deletes are idempotent, so this is safe after partial failure. The app DELETE does not find or remove any local downloaded/exported copy. Treat the receipt as a capability: anyone who has it can request service-side deletion.
- The rate limiter uses a single account-wide counter (30 calls per 60 seconds), so it never needs a client IP key. It is deliberately coarse and shared by all users; Cloudflare describes this binding as a soft limit, not a precise abuse-control or quota system.

## Create and deploy

Prerequisites: Node.js 20 or later, Wrangler 4.36.0 or later (for `ratelimits`), a Cloudflare account with Workers, Workers KV, R2, and Durable Objects enabled, and an account-scoped API token with only the permissions needed for the operation. No credentials belong in this folder or repository. Before deploying this version, create the configured `sudoku-buddy-training-examples` R2 bucket as private; do not enable public access. The `v1` migration provisions the SQLite-backed `ReportReceipt` class. This change does not create the bucket or deploy the Worker.

The private namespace and current Worker are already created and deployed. The endpoint is `https://sudoku-buddy-feedback.antoni-ivanov.workers.dev/v1/reports`; the private KV namespace ID and rate-limit configuration are recorded in `wrangler.toml`. This source change is not deployed, and the configured private R2 bucket must exist before deployment. Do not send corpus or personal test photos during infrastructure checks. Future deployments require an authorized Wrangler session and a review of the current account configuration.

## Private review and export

Do not export or download reports from KV, and do not review them locally, until a receipt-complete deletion mechanism for every local copy is implemented and verified. Existing export/download scripts and the local purge task do not make the app's DELETE request remove those copies. The app's DELETE route removes service-side KV and R2 objects only; it cannot reach a review workspace, workstation temp files, backups, or other local copies. Keep the export workflow disabled until the local deletion gap is closed and the existing-export inventory has been reconciled. There is no public report retrieval route.

The 90-day expiry applies to the analysis-only KV copy. A report with explicit training consent also has a separate private R2 copy that remains until a receipt deletion succeeds. No-consent reports are not copied into the training corpus. A future local review workflow must preserve that distinction and must not present the service-side DELETE as proof that local copies were removed. After the server confirms deletion, the app removes its on-device submission receipt; the original puzzle history remains.

## Privacy and operational limits

The Worker does not log report requests, store client IP addresses, keep report metadata, or expose a read route. Both uploads and deletes share the account-wide rate-limit counter; valid deletes fail closed if that limiter is unavailable or exhausted, before the Worker reads or changes report stores. The per-receipt queue avoids `blockConcurrencyWhile`'s 30-second callback timeout. Cloudflare keeps a Durable Object active while requests and pending I/O are in flight, but runtime updates can stop in-flight requests and service operations still have platform timeouts. The durable expiry, write marker, and deletion tombstone make ordinary retries safe; local Node tests do not simulate forced runtime shutdown while a remote write is committing. Treat that as a deployment validation requirement: test the 20 MiB upload and a delete racing the upload against local Wrangler, and do not treat a `503` as completed submission or deletion. `observability.enabled = false` disables Worker observability configured here; Cloudflare may separately process network and security telemetry under its own service terms. KV is eventually consistent. Expiration and direct deletion remove the KV object, but propagation through Cloudflare's network can take time; R2 deletion is strongly consistent. Service-side deletion does not verify or delete any local copies.

The ZIP signature check does not validate archive members or protect a reviewer from malformed ZIP bombs. Keep the hard cap and never automatically extract untrusted files. Workers KV is suitable only for the initial low-volume bounded analysis queue: it has eventual consistency, bounded account storage, and no atomic conditional writes. R2 is reserved for reports with explicit training consent and is long-lived until deletion is requested. The per-receipt Durable Object retains a small deletion tombstone indefinitely for each deleted receipt so delayed/retried uploads cannot restore the report.
